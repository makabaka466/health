# 健康数据加密说明

本文档说明当前项目中健康数据的加密、授权与验真流程，重点解释 `DEK + 公钥包装` 方案。

## 1. 目标

系统同时满足三件事：

- 链下数据库不存储可直接读取的私密明文。
- 数据所有者可把“某一条记录”授权给被授权者查看。
- 不暴露用户私钥，授权后也不需要手工传递私钥。

## 2. 当前加密模式

### 2.1 公共数据（`is_public=true`）

- 使用服务端统一存储密钥（由 `SECRET_KEY` 派生）加密后入库。
- 业务上可公开访问，但数据库层面仍是密文。

### 2.2 私密数据（`is_public=false`）

采用 `DEK + 公钥包装`：

1. 每条私密记录生成一个随机 `DEK`（32 字节）。
2. 用 `DEK` 加密正文或文件内容。
3. 再用“所有者公钥”把 `DEK` 包装一份，保存到 `owner_encrypted_dek`。
4. 记录 `encryption_version=dek_v1`。

这样做的好处：

- 私密内容不是直接用私钥加密，便于按记录授权。
- 授权时只需把同一个 `DEK` 再包装给被授权者，不需要泄露任何私钥。

## 3. 授权模型

新增授权表：`health_data_grants`，核心字段：

- `record_id`：被授权的数据记录 ID。
- `owner_user_id`：授权方（记录所有者）。
- `grantee_user_id`：被授权方。
- `wrapped_dek`：用被授权方公钥包装后的 DEK。
- `expires_at`、`revoked_at`：过期与撤销控制。

## 4. 授权流程

1. 所有者选择一条私密记录并发起授权。
2. 后端先用所有者私钥解包 `owner_encrypted_dek`，拿到原始 DEK。
3. 后端用被授权用户公钥重新包装 DEK，写入 `health_data_grants.wrapped_dek`。
4. 被授权方查看时，用自己的私钥解包该 `wrapped_dek`，得到 DEK 后解密记录。

说明：

- 全流程不传递所有者私钥。
- 只分发“被授权者可解包的 DEK 包装密文”。

## 5. 主要接口

### 5.1 记录与授权管理（所有者）

- `POST /api/health/records/{record_id}/grants`：创建/更新授权。
- `GET /api/health/records/{record_id}/grants`：查看该记录授权列表。
- `DELETE /api/health/grants/{grant_id}`：撤销授权。
- `GET /api/health/grantable-users`：可授权用户列表。

### 5.2 被授权查看

- `GET /api/health/shared/records`：查看当前用户被授权的记录列表。
- `GET /api/health/shared/records/{record_id}`：查看单条被授权记录。

接口仅返回“未撤销、未过期、`can_read=true`”的授权记录。

## 6. 验真与上链关系

- 链上存的是哈希/摘要与元数据，不存私密明文。
- 验真时比较“当前可还原内容的哈希”与链上哈希是否一致。
- 私密数据只有在可解密（所有者或被授权方）时，才能完成内容级验真；否则会返回未解锁状态。

## 7. 兼容策略

- 老数据若仍是旧加密模式，在首次授权时会尝试迁移为 `dek_v1`。
- 新建私密记录默认采用 `DEK + 公钥包装`。

## 8. 安全要点

- 私钥只用于本方解包 DEK，不用于直接共享。
- 授权可按记录粒度管理，支持过期与撤销。
- 数据库泄露时，攻击者拿到的是密文与包装后的 DEK，无法直接还原明文。

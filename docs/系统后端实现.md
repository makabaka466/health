# 系统后端实现

## 1. 后端总体实现思路

本系统后端采用 `FastAPI + SQLAlchemy + Pydantic` 的技术组合，实现了“健康数据管理 + 隐私加密 + 链上验真 + 智能问答 + 知识库检索 + 管理员运维”一体化能力。

后端采用分层设计：

- 控制层（Controller）：处理路由、参数接收、权限校验、响应输出。
- 服务层（Service）：封装业务逻辑与跨模块协作。
- 实体层（Entity/Model）：定义数据库表结构与关系映射。
- 模式层（Schema）：定义请求体与响应体，统一接口数据结构。

该结构使系统具备良好的可维护性和可扩展性，便于后续新增医生端、审批流程、任务队列等能力。

## 2. 工程结构与模块划分

以 `backend/app` 为核心目录，主要模块如下：

- `main.py`：FastAPI 应用入口，完成 CORS、路由注册、启动初始化。
- `config.py`：统一配置管理（数据库、JWT、AI、RAG、区块链等）。
- `database.py`：数据库引擎、会话工厂、建表与字段补齐逻辑。
- `schemas.py`：Pydantic 数据模型。
- `controller/`：业务控制器。
  - `auth_controller.py`
  - `health_data_controller.py`
  - `ai_controller.py`
  - `knowledge_controller.py`
  - `admin_controller.py`
- `service/`：业务服务。
  - `auth_service.py`
  - `auth_profile_service.py`
  - `ai_service.py`
  - `admin_service.py`
  - `blockchain_service.py`
  - `blockchain_encryption_service.py`
  - `rag_index_service.py`
- `entity/`：ORM 实体定义。
  - `user.py`
  - `health_data.py`
  - `health_data_grant.py`
  - `chat_message.py`
  - `health_article.py`
  - `rag_knowledge_document.py`
  - `rag_knowledge_chunk.py`
  - `system_setting.py`
  - `system_log.py`

为兼容历史代码，`features/*` 下保留了部分转发导出文件，当前实际实现以 `controller + service + entity` 为主。

## 3. 路由组织与请求流程

系统在 `main.py` 中统一注册以下路由前缀：

- `/api/auth`：用户注册、登录、个人资料、管理员用户管理。
- `/api/health`：健康记录管理、授权管理、共享记录查看。
- `/api/ai`：智能问答、流式问答、问答历史、AI首页建议。
- `/api/knowledge`：知识中心、文章管理、RAG文档与向量管理。
- `/api/admin/system`：系统设置、系统日志、健康记录审计接口。

典型请求处理流程：

1. 前端发起 HTTP 请求。
2. 控制器接收请求并执行鉴权依赖。
3. 服务层处理业务逻辑。
4. 访问数据库、区块链或 AI 服务。
5. 返回标准化响应给前端。

## 4. 数据库与实体模型实现

### 4.1 数据库连接与会话管理

`database.py` 中通过 `create_engine` 创建数据库连接，`SessionLocal` 管理会话，`get_db()` 以依赖注入方式提供请求级数据库会话。

### 4.2 自动建表与增量字段补齐

系统在启动时执行 `init_db()`：

- `Base.metadata.create_all()` 完成基础建表。
- `_ensure_schema_updates()` 对历史数据库执行字段补齐（如 `users.encryption_public_key`、`health_data_user.owner_encrypted_dek`、`encryption_version` 等）。

该策略可在毕业设计环境下减少手工迁移成本，保证功能迭代时旧库可平滑兼容。

### 4.3 核心数据表

1. `users`：用户基本信息、角色、钱包地址、私钥托管密文、加密公钥、公开/私密档案等。  
2. `health_data_user`：健康记录主体，包含文本/文件密文、公开标识、链上标识、DEK包裹信息。  
3. `health_data_grants`：记录级授权关系，包含授权方、被授权方、包装后的DEK、有效期、撤销状态。  
4. `chat_messages`：AI对话历史。  
5. `rag_knowledge_documents`、`rag_knowledge_chunks`：知识库文档与分块。  
6. `health_articles`、`article_favorites`、`article_read_history`：知识中心文章及用户行为数据。  
7. `system_settings`、`system_logs`：系统参数与审计日志。

## 5. 认证鉴权与权限控制

### 5.1 登录注册与JWT机制

`auth_service.py` 实现用户注册、用户登录、管理员登录、第三方登录流程，登录成功后签发 JWT Token。

- 普通用户使用 `token`。
- 管理员使用 `adminToken`。

前后端通过 Bearer Token 完成鉴权。

### 5.2 角色权限隔离

系统通过依赖注入进行权限校验：

- 普通业务接口要求用户登录。
- 管理接口要求管理员身份。

前端路由守卫与后端权限依赖形成双层保护，避免未授权访问。

### 5.3 用户隐私信息保护

邮箱、钱包地址、社交 OpenID 等敏感字段采用“脱敏展示 + 哈希索引 + 密文存储”策略，兼顾查询能力与隐私保护。

## 6. 健康数据管理实现

`health_data_controller.py` 提供健康数据核心接口：

- 新增记录：`POST /api/health/records`
- 查询列表：`GET /api/health/records`
- 查询详情：`GET /api/health/records/{id}`
- 更新记录：`PUT /api/health/records/{id}`
- 删除记录：`DELETE /api/health/records/{id}`
- 公开记录：`/api/health/public/records...`
- 汇总与分析：`/api/health/summary`、`/api/health/analyze`

### 6.1 多类型数据处理

系统支持 `text / pdf / word` 三类记录：

- 文本记录：结构化 JSON 文本入库。
- 文件记录：前端上传 Base64，后端进行 MIME、文件头、大小校验后处理。

### 6.2 链上验真协同

记录创建和更新时计算内容哈希，并调用区块链服务写入链上存证；读取时根据链上记录比对哈希，返回验真状态与提示信息。

## 7. 加密与授权机制实现

本系统私密数据采用 `DEK + 公钥包装（Envelope Encryption）`：

1. 每条私密记录生成随机 DEK（数据密钥）。
2. 使用 DEK 加密文本或文件内容。
3. DEK 再用所有者公钥包装，保存到 `owner_encrypted_dek`。
4. `encryption_version` 标记为 `dek_v1`。

加密工具位于 `blockchain_encryption_service.py`，包含：

- 文本/二进制加解密（含 DEK 版本）。
- 私钥规范化、地址推导、公钥推导。
- DEK 生成、包装与解包。

### 7.1 授权接口

授权通过 `health_data_grants` 表管理，支持：

- 可授权用户列表：`GET /api/health/grantable-users`
- 授权列表：`GET /api/health/records/{record_id}/grants`
- 创建授权：`POST /api/health/records/{record_id}/grants`
- 撤销授权：`DELETE /api/health/grants/{grant_id}`

授权时系统会将同一 DEK 用被授权者公钥重新包装，写入 `wrapped_dek`，不泄露任何私钥。

### 7.2 被授权查看

新增共享查看接口：

- `GET /api/health/shared/records`
- `GET /api/health/shared/records/{record_id}`

被授权方使用自己的私钥解包 `wrapped_dek` 后读取明文，实现“授权可读、未授权不可读”。同时校验 `can_read`、`expires_at`、`revoked_at` 等授权状态。

## 8. AI问答服务实现

`ai_controller.py + ai_service.py` 实现问答能力：

- 普通问答接口。
- SSE 流式问答接口。
- 会话历史读取与管理。
- 首页 AI 建议生成与缓存。

### 8.1 流式输出机制

后端将模型输出拆分为事件流（meta/status/delta/done），前端按增量拼接，实现接近实时的响应体验。

### 8.2 上下文融合策略

AI 问答上下文可综合：

- 公共健康数据。
- 用户公开档案。
- 用户显式选择的私密上下文（受控解密）。
- RAG 知识库检索结果。

该机制使回复兼顾“通用医学知识”与“个体化场景”。

## 9. 知识库与文章服务实现

`knowledge_controller.py` 提供：

1. 文章管理：新增、编辑、删除、查询、导入。  
2. 用户行为：收藏、阅读历史。  
3. RAG文档管理：文档CRUD、批量导入、分块状态查询、向量详情查看。  

`rag_index_service.py` 负责：

- 文档分块。
- 向量生成。
- 向量库写入与删除。
- 检索阶段召回。

管理员可在前端直接查看分块数量、向量存在性、维度和 point_id，用于排查索引质量。

---

## 10. 区块链服务实现

`blockchain_service.py` 提供链上能力：

- 健康记录哈希写入。
- 记录更新。
- 链上信息查询。
- 新用户测试 ETH 发放（可配置）。

当区块链服务不可用时，系统采用降级策略：核心业务可继续执行，仅关闭链上写入或返回对应提示，避免系统整体不可用。

---

## 11. 管理员系统服务实现

`admin_controller.py + admin_service.py` 负责后台运维能力：

- 系统设置读取与更新。
- 系统日志查询。
- 健康记录审计列表与详情。
- 操作行为日志写入（用户状态变更、记录操作、系统设置等）。

日志字段包含 `level/module/action/message/operator_id/created_at`，可支持问题追踪与审计复盘。

## 12. 接口规范与异常处理

### 12.1 参数校验

通过 Pydantic Schema 完成字段类型、长度、范围、必填校验，控制器层对业务条件进行补充校验（如私钥是否可用、记录归属是否合法）。

### 12.2 状态码设计

- `200`：请求成功。
- `400`：参数或业务条件不满足。
- `401`：认证失败或令牌失效。
- `403`：越权访问。
- `404`：资源不存在。
- `500`：服务内部错误。

### 12.3 异常兜底

对链上查询、文件解析、AI输出、密钥解包等高风险环节均进行了异常捕获与友好提示，避免异常直接暴露到前端。

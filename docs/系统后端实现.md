# 系统实现章节：后端实现

## 1. 后端总体实现思路

本系统后端采用 `FastAPI` 作为 Web 服务框架，结合 `SQLAlchemy` 完成数据库访问，使用 `Pydantic` 进行请求与响应数据建模，并通过 `JWT` 实现身份认证。在此基础上，系统进一步集成了本地大模型推理、RAG 知识检索、健康数据加密存储、区块链链上存证以及系统日志等功能，从而形成了一个兼具业务处理能力与扩展能力的后端服务体系。

从代码结构来看，后端整体采用“入口层 + 基础设施层 + 业务功能模块层”的组织方式：

- **入口层**
  - `backend/app/main.py`
  - 负责创建 FastAPI 应用、配置跨域、注册路由以及在启动阶段初始化数据库。
- **基础设施层**
  - `backend/app/config.py`
  - `backend/app/database.py`
  - `backend/app/models.py`
  - `backend/app/schemas.py`
  - 负责配置管理、数据库连接、ORM 模型和接口数据结构。
- **业务功能层**
  - 位于 `backend/app/features/` 目录下，按照功能模块划分为：
    - `auth`
    - `health_data`
    - `ai`
    - `knowledge`
    - `admin`
    - `rag`
    - `blockchain`

这种模块化划分方式使得每个业务子系统都具有相对独立的路由、服务和辅助逻辑，便于后续迭代开发与论文中的结构化描述。

## 2. 后端应用入口与路由组织实现

后端应用入口文件为 `backend/app/main.py`。在该文件中，系统首先创建 `FastAPI` 实例，并设置项目标题、描述和版本号。随后通过 `CORSMiddleware` 配置跨域访问，允许前端开发环境地址访问后端接口。

在路由组织方面，系统将不同业务模块分别注册到统一 API 前缀下，具体包括：

- `/api/auth`：认证与用户相关接口
- `/api/health`：健康数据接口
- `/api/ai`：智能问答与 AI 分析接口
- `/api/knowledge`：健康知识中心接口
- `/api/admin/system`：管理员系统设置与日志接口

这种路由设计具有以下优点：

- 业务边界清晰，不同模块的接口互不混杂；
- 便于前后端对接时统一命名和维护；
- 在论文中可以明确划分系统功能模块及其 API 入口。

此外，在应用启动阶段，系统通过 `@app.on_event("startup")` 调用 `init_db()` 完成数据库初始化。这意味着后端服务在启动时不仅会加载应用本身，还会自动处理表结构创建、字段补全和初始管理员用户创建等工作，从而降低了部署和初始化成本。

## 3. 配置管理与数据库基础设施实现

### 3.1 配置管理实现

系统配置集中定义在 `backend/app/config.py` 中。该文件使用 `Settings` 类统一管理项目运行所需的各类参数，并支持通过环境变量进行覆盖。配置内容主要包括：

- **数据库配置**
  - MySQL 主机、端口、用户名、密码和数据库名
  - 组合得到 `DATABASE_URL`
- **JWT 配置**
  - `SECRET_KEY`
  - `ALGORITHM`
  - `ACCESS_TOKEN_EXPIRE_MINUTES`
- **管理员默认账号配置**
  - 初始管理员用户名、邮箱、密码、管理员注册密钥
- **本地大模型配置**
  - Ollama 服务地址、模型名称、超时、采样参数等
- **RAG 配置**
  - 向量集合名称、向量检索 TopK、分块大小、相似度阈值等
- **区块链配置**
  - Web3 RPC 地址
  - 健康数据合约地址
  - 合约 ABI
  - 自动发放测试 ETH 的配置

这种集中式配置管理实现的优势在于：

- 降低硬编码风险；
- 提升开发、测试和部署环境之间的切换灵活性；
- 便于论文中说明系统的可部署性和工程化设计。

### 3.2 数据库连接与会话管理实现

数据库访问层位于 `backend/app/database.py`。该文件使用 SQLAlchemy 完成以下工作：

- 创建数据库引擎 `engine`
- 创建会话工厂 `SessionLocal`
- 创建 ORM 基类 `Base`
- 提供请求级数据库依赖 `get_db()`

其中，`get_db()` 采用生成器方式为每次请求创建独立数据库会话，并在请求结束后自动关闭。这种实现与 FastAPI 的依赖注入机制结合后，可以保证数据库连接的生命周期清晰且安全。

### 3.3 启动期自动补字段机制实现

除常规的 `Base.metadata.create_all()` 外，系统还实现了 `_ensure_schema_updates()` 方法，用于在启动时检查数据库中是否缺少关键字段或新增表，并通过 `ALTER TABLE` 自动补齐。这一机制主要用于处理项目演进过程中旧库结构与新版本代码之间的兼容问题。

例如，系统会自动检查并补充：

- `users` 表中的加密字段、哈希字段、社交登录字段和首页 AI 建议缓存字段；
- `chat_messages` 表中的 `session_id` 字段；
- `health_data_user` 表中的加密数据字段、公开状态字段和链上字段；
- RAG 文档与分块表是否存在。

从工程实践上看，这种设计使系统具备一定的“自适应迁移”能力，减少了因数据库版本不一致而导致的启动失败问题。

## 4. 数据模型与接口数据结构实现

### 4.1 ORM 数据模型实现

系统核心数据库模型定义在 `backend/app/models.py` 中，主要包括以下几类表：

- **用户与权限相关表**
  - `Role`
  - `User`
- **健康数据相关表**
  - `HealthData`
- **智能问答相关表**
  - `ChatMessage`
- **健康知识相关表**
  - `HealthArticle`
  - `ArticleFavorite`
  - `ArticleReadHistory`
- **RAG 知识库相关表**
  - `RagKnowledgeDocument`
  - `RagKnowledgeChunk`
- **系统管理相关表**
  - `SystemSetting`
  - `SystemLog`

其中，`User` 模型不仅包含用户名、邮箱、密码等基础信息，还包含：

- 加密邮箱与邮箱哈希
- 钱包地址与钱包地址哈希
- 私钥相关字段
- 公开/私密个人资料字段
- 社交登录提供方与第三方 open_id 字段
- 首页 AI 建议缓存字段

这说明系统后端在用户模型设计上不仅考虑了传统认证需求，也兼顾了隐私保护、区块链身份以及智能推荐等扩展能力。

在健康数据模型 `HealthData` 中，系统同时支持：

- 文本健康数据
- 文件型健康数据（PDF/Word）
- 加密后的文本内容与文件内容
- 是否公开
- 链上数据 ID 与交易哈希

因此，后端数据模型能够很好地支撑“健康数据加密 + 可选公开 + 链上存证”的复合业务场景。

### 4.2 Pydantic 数据结构实现

接口层的数据模型位于 `backend/app/schemas.py`。该文件使用 `Pydantic` 对请求参数和响应结构进行统一建模，主要作用包括：

- 对前端提交的数据进行类型校验；
- 定义接口返回结果结构；
- 将 ORM 对象与 JSON 响应进行结构化映射。

例如，系统为以下场景定义了专门的 Schema：

- 用户注册、登录、个人资料
- 健康数据新增、更新、响应
- 智能问答消息与历史记录
- 健康知识文章列表与详情
- RAG 文档增删改查与分块状态
- 管理员系统设置与系统日志

这种“ORM 模型负责持久化、Schema 负责接口边界”的实现模式，是现代 Python Web 后端中较为规范的做法，也有助于保证接口的一致性和可维护性。

## 5. 用户认证与权限控制的后端实现

认证模块主要位于 `backend/app/features/auth/` 目录下，包括：

- `router.py`
- `service.py`
- `dependencies.py`
- `profile_service.py`

### 5.1 认证核心流程实现

在普通登录流程中，后端首先通过 `AuthService.authenticate()` 根据用户名查询用户，并校验密码哈希。验证通过后，再由 `create_access_token()` 生成 JWT 令牌，并返回给前端。

在管理员登录流程中，系统基于普通登录逻辑进一步增加角色校验，通过 `authenticate_admin()` 确保当前账号属于 `admin` 或 `super_admin`。这体现了系统在认证上采用了“统一账号体系 + 角色区分”的设计思路。

### 5.2 JWT 鉴权实现

JWT 创建与解析逻辑位于 `auth/dependencies.py` 中。系统通过以下步骤完成接口鉴权：

1. 前端在请求头中携带 `Bearer Token`。
2. 后端通过 `OAuth2PasswordBearer` 提取令牌。
3. 使用 `jose.jwt.decode()` 对令牌进行解码。
4. 从载荷中提取用户名 `sub`。
5. 再通过 `AuthService.get_user_by_username()` 查询数据库中的用户对象。

若令牌无效或用户不存在，则抛出 `401 Unauthorized` 异常。对于仅管理员可访问的接口，系统还进一步通过 `get_current_admin()` 校验角色，不满足条件则返回 `403 Forbidden`。

### 5.3 注册与社交登录实现

在用户注册方面，`AuthService.register()` 除完成用户名、邮箱、密码等基础账号创建外，还会自动生成钱包私钥、钱包地址，并根据配置尝试为新用户发放测试链 ETH。这说明系统后端在注册时已将账号与区块链身份进行绑定。

在第三方登录方面，系统实现了社交登录初始化与资料补全两阶段流程：

- **初始化阶段**
  - 根据第三方平台和授权码构造社交票据 `social_ticket`
- **资料补全阶段**
  - 将第三方身份与系统内用户资料绑定，完成系统账号创建与登录

这一机制保证了第三方身份接入过程中的灵活性，也使后端认证能力不局限于传统用户名密码模式。

### 5.4 个人资料服务实现

用户个人资料功能由 `profile_service.py` 实现。核心方法 `upsert_profile()` 会根据用户私钥对资料进行加密，并根据用户选择决定是否保存公开资料副本：

- `encrypted_profile_data`：始终保存加密后的档案
- `public_profile_data`：仅在资料设为公开时保存明文版本
- `profile_is_public`：标记当前资料是否公开

此外，如果用户公开资料发生变化，系统还会调用 AI 模块的缓存失效逻辑，使首页 AI 建议能够及时更新。这体现了后端各功能模块之间的协同关系。

## 6. 健康数据管理的后端实现

健康数据模块主要由 `backend/app/features/health_data/router.py` 实现。该模块承担了健康数据的上传、查询、更新、删除、摘要统计和分析请求处理。

### 6.1 健康数据接收与类型处理实现

系统支持三种健康数据类型：

- 文本型数据 `text`
- PDF 文件 `pdf`
- Word 文件 `word`

在新增和修改健康数据时，后端首先通过 `_normalized_file_type()` 对文件类型进行统一化处理，再调用 `_decode_upload_data()` 对前端提交的 Base64 文件数据进行解码、文件头校验和大小校验。该函数会依据不同类型限制上传大小，并通过文件特征判断是否为真实 PDF 或 Word 文件，从而避免非法内容写入数据库。

### 6.2 加密存储实现

健康数据的一个关键特点是支持公开与私密两种存储模式。

当用户提交健康记录时，后端会先通过 `_resolve_effective_private_key()` 获取可用私钥，随后依据数据公开状态分别处理：

- **公开数据**
  - 使用系统统一的公开存储密钥加密后写入数据库
- **私密数据**
  - 使用用户私钥加密后写入数据库

文本型数据会写入 `encrypted_data_content`，文件型数据会写入 `encrypted_pdf_data`。系统并不依赖数据库直接保存明文，从而满足隐私保护的要求。

### 6.3 健康数据读取与解密实现

后端在返回健康数据给前端时，并不是简单返回数据库原始字段，而是通过 `_serialize_record()` 统一序列化。该过程内部会调用：

- `_resolve_record_values()`：根据是否公开、是否提供私钥，尝试解密真实内容
- `_verify_record_onchain()`：校验当前记录链上哈希是否与本地数据一致

序列化结果中不仅包含数据内容，还包含：

- `requires_private_key`：是否需要私钥才能查看
- `onchain_verification_status`：链上校验状态
- `onchain_data_id`：链上记录 ID
- `onchain_tx_hash`：链上交易哈希
- `onchain_verification_message`：校验说明

因此，后端在健康数据接口中同时承担了“解密、校验、封装展示数据”的职责。

### 6.4 健康数据统计与分析实现

系统后端还提供健康摘要与分析接口：

- `/health/summary`：统计用户健康记录数量、本月记录数、平均体重、平均心率等
- `/health/analyze`：对指定时间范围内的健康数据进行分析并返回建议

在分析实现中，后端会遍历用户健康记录，从文本内容中提取结构化指标，并依据血压、心率、血糖等阈值生成基础健康建议。这说明系统后端并未将健康分析完全依赖于大模型，而是保留了一部分规则驱动的业务分析能力。

## 7. 智能问答服务的后端实现

智能问答模块主要由 `backend/app/features/ai/router.py` 和 `backend/app/features/ai/service.py` 实现。该模块负责 AI 问答请求处理、上下文构建、聊天历史维护以及首页智能建议生成。

### 7.1 AI 问答请求处理实现

在问答路由层，系统会接收用户问题后综合构造上下文信息，主要包括：

- 当前用户的公开档案摘要
- 用户公开健康数据上下文
- 用户授权的私密数据上下文
- RAG 检索返回的知识片段
- 历史聊天内容

然后将这些上下文与用户问题拼接为模型输入，调用本地 Ollama 模型完成推理生成。

### 7.2 私密上下文与公开上下文构建实现

AI 服务层通过多个辅助函数完成健康上下文的组织：

- `public_profile_summary()`：生成公开个人档案摘要
- `build_public_health_context()`：生成公开健康记录上下文
- `build_private_context_options()`：返回当前用户可授权使用的私密数据选项
- `build_private_context()`：根据用户选择的私密数据项构造私密上下文文本
- `build_record_context()`：将单条健康记录转换为 AI 可理解的上下文片段

对于 PDF 记录，系统会先提取 PDF 文本，再进行摘要截断；对于文本型记录，则会解析其中的指标并生成更结构化的描述。该实现说明后端在 AI 问答中并非简单传递数据库原始内容，而是进行了面向模型输入的上下文压缩与整理。

### 7.3 流式输出实现

智能问答接口不仅支持普通问答，还支持流式输出。在流式模式下，后端使用 `StreamingResponse` 持续向前端推送事件数据，事件类型包括：

- `meta`
- `status`
- `delta`
- `done`
- `error`

其中：

- `meta` 用于通知前端当前对话 ID、参考文献、是否使用个性化数据；
- `status` 用于展示检索中、生成中等状态；
- `delta` 用于持续追加模型生成内容；
- `done` 表示本次回答结束；
- `error` 用于异常反馈。

这种实现方式与前端的流式读取能力相配合，使系统具备更自然的智能问答交互体验。

### 7.4 首页 AI 建议缓存实现

系统还实现了首页 AI 建议功能。后端通过：

- `load_cached_home_advice()`
- `save_user_home_advice_payload()`
- `invalidate_user_home_advice()`

对首页个性化建议结果进行缓存与失效控制。这样可以减少重复调用模型所带来的响应开销，提高首页访问性能。

## 8. 健康知识中心与 RAG 知识库的后端实现

健康知识模块主要位于 `backend/app/features/knowledge/router.py`，RAG 索引能力则位于 `backend/app/features/rag/` 目录下。

### 8.1 健康文章服务实现

知识中心基础文章功能包括：

- 文章列表查询
- 文章详情查看
- 文章收藏与取消收藏
- 阅读记录写入与查询
- 首页推荐内容生成

在文章详情接口中，后端会自动增加文章浏览量，并记录用户阅读历史。收藏功能则通过 `ArticleFavorite` 表维护用户与文章之间的多对多关系。阅读记录通过 `ArticleReadHistory` 进行累计更新，从而支撑前端“最近阅读”与“阅读次数统计”的展示。

### 8.2 文章管理与导入实现

管理员端可以新增、修改、删除和批量导入健康文章。导入功能支持上传文件并自动提取文本内容，随后由后端构造成文章摘要和正文，实现批量知识入库。这表明后端在知识中心部分不仅支持普通内容管理，也支持更高效的资料录入方式。

### 8.3 RAG 文档管理实现

系统将面向 AI 检索的知识库文档单独建模为：

- `RagKnowledgeDocument`
- `RagKnowledgeChunk`

管理员可以通过接口新增、修改、删除和导入知识库文档。后端在文档写入数据库后，会自动调用 `_sync_rag_index_safely()`，将文档内容同步到 RAG 索引体系中。

### 8.4 RAG 索引构建实现

RAG 相关核心逻辑位于 `rag/index_service.py`。其主要流程为：

1. 将文档正文按指定长度切分为多个文本块；
2. 为每个分块调用 embedding 模型生成向量；
3. 确保向量库集合存在；
4. 将向量及其元数据写入 Qdrant；
5. 同时将分块信息记录到本地数据库 `rag_knowledge_chunks` 表。

在文档修改或停用时，后端会删除旧的向量点并重建索引，确保数据库与向量库状态一致。这样，系统就形成了“关系型数据库保存文档结构，向量数据库保存语义向量”的双层知识管理模式。

### 8.5 RAG 检索实现

在实际问答中，后端调用 `search_rag_knowledge()` 完成语义检索。该函数先为用户问题生成查询向量，再向向量库搜索相似分块，并将结果封装为 `RagSearchHit` 结构返回。每条结果都包含：

- 文档 ID
- 文档标题
- 分类
- 来源
- 标签
- 分块内容
- 分块序号
- 相似度分数

此后，这些检索结果会被拼接进 AI 的提示上下文中，作为生成回答的参考知识来源，从而提升问答质量与专业性。

## 9. 区块链服务的后端实现

区块链功能位于 `backend/app/features/blockchain/service.py`。系统在该模块中定义了 `HealthDataChainService`，用于连接 EVM 兼容链并操作健康数据合约。

### 9.1 链接与合约初始化实现

服务初始化时，系统会：

- 通过 `WEB3_PROVIDER_URI` 连接链节点；
- 读取配置中的健康数据合约地址和 ABI；
- 校验合约地址上是否存在已部署代码；
- 若校验通过，则构造合约对象用于后续调用。

若链服务不可用或合约不存在，则系统会自动关闭链上功能，而不会影响整体后端基础业务运行。这说明区块链模块在系统中属于“增强型能力”，不是单点依赖。

### 9.2 健康数据链上存证实现

在新增或修改健康数据时，后端会先根据健康数据原始内容构造摘要源，再通过 SHA-256 生成哈希值，随后调用区块链服务完成：

- `store_health_data()`：首次上链
- `update_health_data()`：更新链上记录
- `get_health_record()`：查询链上记录

数据库中会同步记录：

- `onchain_data_id`
- `onchain_tx_hash`

这样一来，系统可以在后续读取数据时重新计算当前数据哈希，并与链上记录进行对比，判断健康数据是否被篡改。

### 9.3 注册自动发放测试资产实现

系统还支持为新注册用户自动发放测试 ETH。该功能同样依赖区块链服务，通过配置项控制是否启用和发放额度。这种设计主要用于开发和演示环境，目的是降低新用户参与链上交互的门槛。

## 10. 系统管理与操作日志的后端实现

系统管理模块主要由 `backend/app/features/admin/router.py` 和 `backend/app/features/admin/service.py` 实现。

### 10.1 系统设置实现

管理员可通过系统设置接口读取和修改系统配置。系统设置保存在 `system_settings` 表中，字段值以 JSON 字符串形式写入数据库。后端在读取时通过 `_parse_value()` 自动反序列化，在更新时通过 `update_settings()` 自动执行写入和提交。

这种设计使部分关键运行参数能够在数据库层进行动态配置，而不必完全依赖环境变量硬编码。

### 10.2 系统日志实现

后端统一通过 `AdminSystemService.log()` 写入系统日志。日志模型 `SystemLog` 主要包括：

- `level`
- `module`
- `action`
- `message`
- `operator_id`
- `created_at`

系统日志的特点在于：

- 支持按模块分类记录操作行为；
- 可通过系统设置控制是否启用操作日志；
- 可记录普通用户与管理员的关键操作。

目前，系统已经将以下操作接入系统日志：

- 用户登录与社交登录
- 用户修改个人资料
- 用户上传、更新、删除健康数据
- 用户收藏与取消收藏文章
- 管理员登录
- 管理员新增、修改、删除健康文章
- 管理员新增、修改、删除知识库文档
- 管理员导入文章和知识库文档
- 管理员修改用户状态与重置密码
- 管理员查看系统设置、查看系统日志、查看健康数据总览
- 管理员修改系统设置

由此可以看出，系统日志模块不仅服务于故障排查，也为系统提供了较完善的审计追踪能力。

## 11. 后端请求处理流程总结

从整体实现角度看，系统后端一次典型请求通常会经历如下流程：

1. 前端发起 HTTP 请求。
2. FastAPI 根据路径分发到对应功能模块路由。
3. 通过依赖注入获取数据库会话及当前用户身份。
4. 使用 Pydantic Schema 完成请求参数校验。
5. 路由层调用服务层或辅助函数处理业务逻辑。
6. 若涉及数据库操作，则通过 SQLAlchemy ORM 读写数据。
7. 若涉及 AI、RAG、加密或区块链，则进一步调用相关模块完成扩展能力处理。
8. 将结果整理为响应结构返回前端。
9. 若该操作属于关键行为，则同步写入系统日志。

这种流程说明，系统后端并不是松散堆叠的接口集合，而是形成了一套较清晰的业务处理链路。

# 健康管理系统核心智能合约代码与接口说明

## 1. 文档说明

### 1.1 文档目的
本文档用于说明健康管理系统核心智能合约的代码结构、关键函数、事件定义、后端接口映射与调用约束，作为开发、联调、测试和运维排障依据。

### 1.2 适用范围
- 合约源码：`contracts/HealthDataAccess.sol`
- 合约编译产物：`contracts/artifacts/HealthDataAccess.json`
- 后端链服务适配：`backend/app/service/blockchain_service.py`
- 健康数据业务入口：`backend/app/controller/health_data_controller.py`
- 运行网络：EVM 兼容链，默认使用 Ganache 本地链

### 1.3 术语说明
- `dataHash`：链下健康数据原文或文件内容计算得到的摘要。
- `encryptedData`：密文摘要或加密片段摘要，链上以 `bytes32` 保存。
- `dataId`：合约内健康数据记录唯一标识。
- `owner`：链上记录所有者，即提交交易的钱包地址。
- 验真：后端重新计算当前业务数据摘要，并与链上保存的哈希值比对。

## 2. 合约总体设计

### 2.1 设计目标
系统采用“链下存原文、链上存摘要”的设计方式，避免将完整健康数据、PDF 文件或隐私内容直接写入区块链。

智能合约主要承担以下职责：
- 保存健康数据摘要与元数据；
- 记录数据所有者；
- 管理公开/私密状态；
- 管理链上授权关系；
- 通过事件记录关键操作，便于后端解析交易结果。

### 2.2 核心合约
核心合约为 `HealthDataAccess`，源码位于：

`contracts/HealthDataAccess.sol`

合约使用 Solidity `^0.8.19`，主要面向 Ganache 或其他 EVM 兼容网络部署。

### 2.3 链上与链下职责划分
- 链下数据库保存健康记录正文、PDF/Word 文件、加密字段、用户授权关系和业务元数据。
- 链上合约保存数据摘要、密文摘要、数据类型、所有者地址、状态与授权信息。
- 后端负责计算摘要、调用合约、解析事件、保存交易哈希与 `dataId`。
- 前端负责展示验真状态和链上存证说明。

## 3. 合约数据结构说明

### 3.1 DataStatus
`DataStatus` 表示健康数据的链上可见性状态：

- `Private`：私密数据，需要所有者或被授权地址读取；
- `Public`：公开数据，任何地址可读取链上元数据。

### 3.2 HealthRecord
`HealthRecord` 是链上健康记录主体结构：

- `bytes32 dataHash`：原始业务数据摘要；
- `bytes32 encryptedData`：密文摘要或加密片段摘要；
- `uint256 timestamp`：链上记录时间；
- `address owner`：数据所有者；
- `bool isActive`：记录是否有效；
- `string dataType`：数据类型，例如 `text`、`pdf`、`word`；
- `DataStatus status`：公开/私密状态。

### 3.3 AccessPermission
`AccessPermission` 表示某地址对某条记录的授权：

- `address requester`：被授权地址；
- `bytes32 dataId`：被授权记录 ID；
- `uint256 grantedAt`：授权时间；
- `uint256 expiresAt`：授权到期时间；
- `bool canRead`：是否可读；
- `bool canWrite`：是否可写；
- `address granter`：授权人。

### 3.4 主要 Mapping
- `healthRecords`：`dataId => HealthRecord`，用于按数据 ID 查询记录；
- `permissions`：`requester => dataId => AccessPermission`，用于查询授权；
- `userRecords`：`owner => dataId[]`，用于查询某用户拥有的全部记录 ID。

## 4. 核心函数说明

### 4.1 storeHealthData
函数签名：

`storeHealthData(bytes32 dataHash, bytes32 encryptedData, string memory dataType) public returns (bytes32)`

功能说明：
- 创建一条新的链上健康数据记录；
- 根据 `msg.sender`、`dataHash` 和 `block.timestamp` 生成 `dataId`；
- 默认将记录状态设置为 `Private`；
- 将 `dataId` 写入当前用户的 `userRecords`；
- 触发 `DataStored` 事件。

调用方：
- 后端 `HealthDataChainService.store_health_data(...)`

主要约束：
- `dataHash` 必须是 32 字节；
- `encryptedData` 必须是 32 字节；
- 同一个 `dataId` 不允许重复写入。

### 4.2 updateHealthData
函数签名：

`updateHealthData(bytes32 dataId, bytes32 newDataHash, bytes32 newEncryptedData) public`

功能说明：
- 更新已有链上记录的数据摘要；
- 更新记录时间戳；
- 触发 `DataUpdated` 事件。

权限要求：
- 调用方必须是记录所有者；
- 或者调用方拥有未过期的写权限。

调用方：
- 后端 `HealthDataChainService.update_health_data(...)`

### 4.3 getHealthData
函数签名：

`getHealthData(bytes32 dataId) public view returns (...)`

功能说明：
- 读取链上健康记录元数据；
- 返回数据摘要、密文摘要、时间戳、所有者和数据类型。

权限要求：
- 所有者可读；
- 公开数据可读；
- 被授权且未过期的地址可读。

### 4.4 grantAccess
函数签名：

`grantAccess(address requester, bytes32 dataId, bool canRead, bool canWrite, uint256 duration) public`

功能说明：
- 记录所有者为指定地址授予读/写权限；
- 授权有效期由 `duration` 指定，单位为秒；
- 触发 `AccessGranted` 事件。

业务说明：
- 当前后端主要采用链下 DEK 授权机制实现私密数据共享；
- 合约授权结构用于链上权限表达，可作为后续链上权限校验扩展基础。

### 4.5 revokeAccess
函数签名：

`revokeAccess(address requester, bytes32 dataId) public`

功能说明：
- 记录所有者撤销指定地址对某条数据的授权；
- 通过 `delete permissions[requester][dataId]` 清除授权；
- 触发 `AccessRevoked` 事件。

### 4.6 makeDataPublic / makeDataPrivate
函数签名：

`makeDataPublic(bytes32 dataId) public`

`makeDataPrivate(bytes32 dataId) public`

功能说明：
- 由记录所有者切换数据公开/私密状态；
- 状态变化时触发 `DataStatusChanged` 事件。

### 4.7 checkPermission / checkAccess
函数签名：

`checkPermission(address requester, bytes32 dataId) public view returns (...)`

`checkAccess(address requester, bytes32 dataId) public view returns (bool)`

功能说明：
- `checkPermission` 返回授权明细；
- `checkAccess` 返回某地址是否可读取某条记录；
- 公开记录、所有者记录、未过期授权均视为可访问。

### 4.8 deleteData
函数签名：

`deleteData(bytes32 dataId) public`

功能说明：
- 记录所有者执行软删除；
- 设置 `isActive=false`；
- 从 `userRecords` 中移除对应 `dataId`。

## 5. 事件说明

### 5.1 DataStored
事件签名：

`DataStored(address indexed owner, bytes32 indexed dataId, string dataType, uint256 timestamp)`

触发时机：
- 调用 `storeHealthData` 成功后触发。

后端用途：
- 后端从交易回执中解析该事件，获取 `dataId` 并保存到业务记录的 `onchain_data_id` 字段。

### 5.2 DataUpdated
事件签名：

`DataUpdated(address indexed owner, bytes32 indexed dataId, uint256 timestamp)`

触发时机：
- 调用 `updateHealthData` 成功后触发。

### 5.3 AccessGranted
事件签名：

`AccessGranted(address indexed granter, address indexed requester, bytes32 indexed dataId, uint256 expiresAt)`

触发时机：
- 调用 `grantAccess` 成功后触发。

### 5.4 AccessRevoked
事件签名：

`AccessRevoked(address indexed granter, address indexed requester, bytes32 indexed dataId)`

触发时机：
- 调用 `revokeAccess` 成功后触发。

### 5.5 DataStatusChanged
事件签名：

`DataStatusChanged(address indexed owner, bytes32 indexed dataId, DataStatus oldStatus, DataStatus newStatus, uint256 timestamp)`

触发时机：
- 数据公开/私密状态切换成功后触发。

----------------------------------------

## 6. 后端链服务接口说明

### 6.1 HealthDataChainService
后端通过 `HealthDataChainService` 统一封装 Web3 调用，核心文件为：

`backend/app/service/blockchain_service.py`

主要职责：
- 初始化 Web3 HTTP Provider；
- 动态检测 Ganache/RPC 连通状态；
- 动态绑定智能合约实例；
- 构造、签名并发送交易；
- 解析交易事件；
- 查询链上记录。

### 6.2 store_health_data
方法作用：
- 调用合约 `storeHealthData`；
- 参数包括用户私钥、业务哈希、密文摘要来源和数据类型；
- 成功后返回交易哈希、交易状态、所有者地址和 `data_id`。

后端调用场景：
- 用户创建健康记录；
- 记录类型可为 `text`、`pdf` 或 `word`。

### 6.3 update_health_data
方法作用：
- 调用合约 `updateHealthData`；
- 用新的摘要更新已有链上记录；
- 成功后沿用原 `data_id` 返回。

后端调用场景：
- 用户编辑健康记录；
- 用户替换 PDF/Word 文件；
- 用户修改公开/私密状态并触发摘要变化。

### 6.4 get_health_record
方法作用：
- 通过 `healthRecords(dataId)` 查询链上记录；
- 返回链上保存的数据哈希、密文摘要、时间戳、所有者、数据类型与状态。

后端调用场景：
- 用户加载健康记录列表；
- 用户查看健康记录详情；
- 系统执行链上验真。

## 7. 业务接口映射

### 7.1 创建健康记录
业务接口：

`POST /api/health/records`

链上动作：
- 计算当前记录摘要；
- 若区块链服务可用，则调用 `storeHealthData`；
- 若区块链服务不可用，则允许上传成功，并返回上链告警。

关键返回字段：
- `onchain_data_id`
- `onchain_tx_hash`
- `onchain_warning`
- `onchain_verification_status`
- `onchain_verification_message`

### 7.2 更新健康记录
业务接口：

`PUT /api/health/records/{record_id}`

链上动作：
- 若已有 `onchain_data_id`，则调用 `updateHealthData`；
- 若没有 `onchain_data_id`，则在链服务可用时尝试新建存证；
- 链服务不可用时不阻断业务更新。

### 7.3 查询与验真
业务接口：

`GET /api/health/records`

`GET /api/health/records/{record_id}`

链上动作：
- 若链服务可用且记录存在 `onchain_data_id`，查询链上记录；
- 重新计算当前数据摘要；
- 对比链上哈希与当前摘要；
- 返回验真状态。

## 8. 验真状态说明

### 8.1 verified
含义：
- 链上哈希与当前业务数据摘要一致；
- 说明当前记录与链上存证匹配。

### 8.2 mismatch
含义：
- 链上哈希与当前业务数据摘要不一致；
- 可能是数据被修改、链上记录未同步或测试环境合约状态变化。

### 8.3 no_proof
含义：
- 当前记录没有链上 `dataId`；
- 通常发生在链服务关闭时上传的记录，或上链未成功的记录。

### 8.4 service_unavailable
含义：
- 区块链服务未启用或 Ganache 未连接；
- 当前记录未执行链上验真。

### 8.5 record_missing
含义：
- 业务库保存了 `onchain_data_id`，但链上找不到对应记录；
- 可能是 Ganache 重置、合约重新部署或链数据丢失。

### 8.6 locked
含义：
- 私密数据未解锁；
- 后端无法得到原文或文件内容，因此无法计算可比对摘要。

----------------------------------------

## 9. Ganache 启停与降级策略

### 9.1 Ganache 未启动
系统行为：
- 用户注册被禁止；
- 健康数据上传、更新和加载不被阻断；
- 验真状态返回 `service_unavailable`；
- 写入接口返回 `onchain_warning`。

### 9.2 Ganache 中途启动
系统行为：
- 后端链服务会动态检测 RPC 状态；
- 用户刷新记录列表或详情时，会重新尝试绑定合约并执行验真；
- 无需重启后端服务。

### 9.3 Ganache 重置或合约重新部署
可能影响：
- 旧 `onchain_data_id` 对应的链上记录可能不存在；
- 验真状态可能变为 `record_missing`；
- 需要重新部署合约并更新后端配置中的合约地址与 ABI。

## 10. 开发与联调注意事项

### 10.1 bytes32 参数要求
合约中的 `dataHash`、`encryptedData` 和 `dataId` 均为 `bytes32`。后端在调用前必须保证十六进制字符串解码后长度为 32 字节。

### 10.2 交易发送要求
交易发送需要：
- 可用的 RPC 节点；
- 可用合约地址；
- 调用方私钥；
- 调用方账户有足够测试 ETH；
- 正确的 `chainId`、`gas` 与 `gasPrice`。

### 10.3 前端展示建议
前端不应只依赖 `onchain_verified` 布尔值，应同时展示：
- `onchain_verification_status`
- `onchain_verification_message`
- `onchain_tx_hash`
- `onchain_data_id`

这样用户能区分“验真失败”“链服务不可用”“未生成存证”等不同情况。

# 健康管理系统系统需求与设计说明书

## 1. 文档说明

### 1.1 文档目的
本文档用于明确健康管理系统的业务需求、功能范围、系统架构、关键设计决策与非功能要求，作为后续开发、测试、部署与验收的统一依据。

### 1.2 适用范围
- 前端：`frontend`（Vue 3 + Element Plus）
- 后端：`backend`（FastAPI + SQLAlchemy）
- 数据层：MySQL（业务库）
- 智能服务：Ollama（对话与建议）、Qdrant（RAG 向量检索）
- 区块链：EVM 网络（默认 Ganache 本地链）

### 1.3 术语说明
- 公开数据：无需私钥即可读取的健康数据。
- 私密数据：需要用户私钥/授权解密的数据。
- 上链存证：将健康数据摘要写入智能合约用于防篡改校验。
- RAG：检索增强生成，通过知识库检索结果增强 AI 回答。

---

## 2. 项目背景与目标

### 2.1 背景
系统面向个人健康数据管理与智能辅助场景，需同时满足：
- 健康数据结构化管理（手动录入 + 文档上传）；
- 数据隐私与授权共享（私密数据可控）；
- 数据可信与可追溯（链上摘要验真）；
- 智能问答与建议（结合用户数据 + 知识库）。

### 2.2 建设目标
- 建立一个可落地运行的“健康数据管理 + AI 助手 + 区块链验真”一体化平台；
- 在区块链服务不可用时，核心业务（注册策略除外）可降级运行；
- 提供可维护、可测试、可扩展的模块化架构。

---

## 3. 用户角色与权限

### 3.1 普通用户（user）
- 可注册、登录、维护个人档案；
- 可新增/编辑/删除健康记录（手动、PDF、Word）；
- 可设置公开/私密；
- 可查看个人记录、摘要、分析、AI 对话；
- 可向管理员授予私密记录读取权限。

### 3.2 管理员（admin）
- 可登录管理端；
- 可查看用户列表、启停用户、重置密码；
- 可查看系统日志和系统设置；
- 可查看健康记录总览及明细（遵循授权与解密策略）；
- 可管理知识库、文章导入与维护。

## 4. 功能需求

### 4.1 认证与账号
- FR-A1：系统支持用户名/密码注册登录。
- FR-A2：系统支持管理员登录入口。
- FR-A3：支持社交登录初始化与资料补全流程。
- FR-A4：注册时生成钱包与私钥材料，并安全保存。
- FR-A5：当区块链 RPC 未连接时，普通注册与社交补全注册应拒绝（返回明确错误）。

### 4.2 健康数据管理
- FR-H1：支持手动录入健康指标（体重、血压、血糖等）与说明文本。
- FR-H2：支持上传 PDF / Word 作为健康记录。
- FR-H3：支持记录公开/私密切换。
- FR-H4：支持记录列表、详情、编辑、删除。
- FR-H5：支持记录汇总统计与趋势分析。

### 4.3 私密数据与授权
- FR-P1：私密记录需解密后可查看。
- FR-P2：支持记录级授权（授予对象、有效期、撤销）。
- FR-P3：被授权对象可在有效期内查看私密记录。
- FR-P4：撤销后应立即失效。

### 4.4 区块链存证与验真
- FR-C1：创建/更新记录时可执行链上存证（条件满足时）。
- FR-C2：返回记录时应给出验真状态与说明字段。
- FR-C3：当链服务不可用时不阻断核心读写，并返回 `service_unavailable` 等可解释状态。
- FR-C4：链服务恢复后，刷新记录应可重新触发验真。

### 4.5 AI 助手与知识库
- FR-I1：支持 AI 聊天（普通与流式 SSE）。
- FR-I2：支持用户选择私密上下文参与问答。
- FR-I3：支持 RAG 检索增强，返回参考来源。
- FR-I4：首页支持自动生成个性化健康建议并缓存。

### 4.6 管理端系统能力
- FR-M1：系统设置可动态生效（维护模式、注册开关、AI 开关等）。
- FR-M2：系统日志可追踪关键操作（登录、上传、授权、设置变更）。
- FR-M3：知识库支持文章与文档导入管理。

## 5. 非功能需求

### 5.1 安全性
- NFR-S1：密码使用安全哈希存储。
- NFR-S2：私钥采用服务端密钥二次加密存储。
- NFR-S3：私密健康数据采用加密存储，需合法密钥或授权方可解密。
- NFR-S4：接口基于 JWT 鉴权，并按角色鉴权。

### 5.2 可用性
- NFR-A1：区块链、Ollama、Qdrant 任一不可用时，系统核心功能应有可预期降级策略。
- NFR-A2：关键错误信息应面向用户可读，面向运维可定位。

### 5.3 性能
- NFR-P1：常规列表接口应支持分页。
- NFR-P2：AI 与文档解析任务采用异步/线程切换避免阻塞主请求线程。

### 5.4 可维护性
- NFR-M1：后端控制层、服务层职责清晰。
- NFR-M2：关键流程有自动化测试覆盖（P0）。
- NFR-M3：配置项集中管理并支持环境变量注入。

## 6. 系统总体设计

### 6.1 架构分层
- 表现层：Vue 前端页面、路由守卫、API 模块封装。
- 接口层：FastAPI 控制器，负责鉴权、参数校验、流程编排。
- 业务层：`service` 模块封装认证、加密、链服务、AI 与管理逻辑。
- 数据层：SQLAlchemy 模型 + MySQL 持久化。
- 外部服务层：Ganache/EVM、Ollama、Qdrant。

### 6.2 关键模块
- 认证模块：`auth_controller.py` + `auth_service.py`
- 健康数据模块：`health_data_controller.py`
- AI 模块：`ai_controller.py` + `ai_service.py`
- 管理模块：`admin_controller.py` + `admin_service.py`
- 链服务模块：`blockchain_service.py`

### 6.3 数据设计要点
- `User`：账号主体、角色、私钥材料、敏感字段哈希。
- `HealthData`：记录内容、文件类型、公开状态、加密字段、链上标识。
- `HealthDataGrant`：记录授权关系与有效期。
- `SystemSetting`：系统动态配置。
- `ChatMessage`：AI 会话消息。

### 6.4 加密与隐私设计
- 公开记录：使用公共存储密钥加密保存。
- 私密记录：使用记录级 DEK 加密，并保存 DEK 包裹数据（`owner_encrypted_dek`）。
- 授权访问：通过授权对象公钥包裹 DEK，实现最小权限解密。

### 6.5 链上设计
- 存证内容：业务数据摘要 + 密文摘要。
- 存证动作：`storeHealthData` / `updateHealthData`。
- 验真动作：查询链上记录并比对摘要。
- 动态可用性：运行中按 RPC 连通状态和合约绑定状态实时判断是否可用。

## 7. 关键业务流程

### 7.1 注册流程
1. 前端提交注册请求；
2. 后端校验维护模式、注册开关、密码规则、区块链可用性；
3. 生成账号与钱包私钥材料并持久化；
4. 返回用户信息与注册结果。

### 7.2 健康记录上传流程
1. 前端提交文本或 PDF/Word；
2. 后端校验类型、大小、内容合法性；
3. 根据公开/私密策略执行加密存储；
4. 若链服务可用则执行上链，否则写 `onchain_warning` 并继续成功返回；
5. 返回记录与验真状态字段。

### 7.3 验真刷新流程
1. 用户刷新列表或详情；
2. 后端读取记录并按当前链服务状态判定；
3. 可用时执行链上比对，不可用时返回 `service_unavailable`。

## 8. 接口设计约束（摘要）

### 8.1 统一约束
- 鉴权方式：`Authorization: Bearer <token>`
- 数据格式：JSON 为主，部分登录接口为表单。
- 错误码：遵循 HTTP 状态码与 `detail` 字段说明。

### 8.2 健康记录响应关键字段
- `onchain_verification_status`：验真状态（如 `verified`、`mismatch`、`service_unavailable`、`no_proof`）
- `onchain_verification_message`：验真说明
- `onchain_warning`：上链告警（写入/更新时）

## 9. 部署与运行前提（需求侧）

### 9.1 必需组件
- Python 3.10+
- Node.js 18+
- MySQL

### 9.2 可选组件（按功能启用）
- Ganache/EVM：链上存证与验真
- Ollama：AI 对话与首页建议
- Qdrant：向量检索

### 9.3 配置要求
- 数据库连接、JWT 密钥、Web3 RPC、合约地址与 ABI、Ollama/Qdrant 地址需通过配置统一管理。

## 10. 风险与约束

### 10.1 技术风险
- 外部依赖（Ganache/Ollama/Qdrant）可用性波动会影响对应能力。
- 链上交易确认延迟可能导致存证结果非实时可见。

### 10.2 业务约束
- 私密数据依赖密钥材料完整性；密钥损坏会影响可解密性。
- 注册策略受区块链可用性门禁影响（当前策略：链不可用则不允许注册）。

---

## 11. 验收标准（建议）

- AC-1：用户可完成注册、登录、健康记录 CRUD。
- AC-2：PDF/Word 上传、查看、编辑替换可用。
- AC-3：私密记录授权与撤销流程可用。
- AC-4：Ganache 关闭时：  
  上传/加载不失败，验真字段有明确“未启用”标注；注册被禁止。
- AC-5：Ganache 启动后刷新可恢复链上验真。
- AC-6：AI 问答、RAG 检索与首页建议在依赖可用时正常工作。

# 系统实现章节：智能合约实现

## 1. 智能合约实现范围说明

本系统智能合约源码位于 `contracts/HealthDataAccess.sol`，后端实际接入与调用的合约也以该合约为核心。其设计目标不是把完整健康数据上链，而是将**可校验的链上元数据**与**访问权限控制**上链，实现“链下存明文/密文大数据，链上存哈希与权限”的架构。

在当前后端实现中，链上交互封装于 `backend/app/features/blockchain/service.py` 的 `HealthDataChainService`，并通过配置项读取合约地址和 ABI：

- 合约地址：`HEALTH_DATA_CONTRACT_ADDRESS`
- 合约 ABI：`HEALTH_DATA_CONTRACT_ABI_JSON`
- ABI 默认来源：`contracts/artifacts/HealthDataAccess.json`

---

## 2. 合约核心数据结构

`HealthDataAccess` 合约主要定义了两个结构体和三个核心映射。

### 2.1 枚举 `DataStatus`

- `Private`：私密数据（默认状态）
- `Public`：公开数据

该状态用于区分链上访问控制策略。

### 2.2 结构体 `HealthRecord`

用于保存单条链上健康记录元数据，字段包括：

- `dataHash`：原始数据哈希
- `encryptedData`：加密摘要（`bytes32`）
- `timestamp`：更新时间戳
- `owner`：数据所有者地址
- `isActive`：是否有效（软删除标志）
- `dataType`：数据类型（文本/PDF/Word等标签）
- `status`：私密或公开

### 2.3 结构体 `AccessPermission`

用于保存访问授权关系，字段包括：

- `requester`：被授权地址
- `dataId`：数据 ID
- `grantedAt`：授权时间
- `expiresAt`：过期时间
- `canRead`：是否可读
- `canWrite`：是否可写
- `granter`：授权者地址

### 2.4 映射与索引结构

- `healthRecords`：`dataId -> HealthRecord`
- `permissions`：`requester -> dataId -> AccessPermission`
- `userRecords`：`owner -> dataId[]`

其中 `userRecords` 用于按用户聚合其名下数据 ID 列表，支持分页前查询或总量统计。

---

## 3. 事件定义与用途

合约定义了以下事件，用于链下监听和审计追踪：

- `DataStored`：新数据写入
- `DataUpdated`：数据哈希或密文摘要更新
- `DataStatusChanged`：私密/公开状态切换
- `AccessGranted`：权限授权
- `AccessRevoked`：权限撤销

这些事件不承担主存储职责，但对前端监听、后端索引和审计日志非常关键。

---

## 4. 权限控制修饰符

合约通过修饰符实现访问控制：

- `onlyDataOwner(dataId)`
  - 仅数据 owner 可调用（例如删除、授权、状态切换）。
- `hasReadPermission(dataId)`
  - owner 可读；公开且激活数据可读；或被授权可读且未过期可读。
- `hasWritePermission(dataId)`
  - owner 可写；或被授权可写且未过期可写。

该设计把“身份”和“时间有效期”同时纳入访问控制逻辑。

## 5. 合约方法说明（方法做什么）

下面按合约中的公开方法逐一说明其功能。

### 5.1 `storeHealthData(bytes32 dataHash, bytes32 encryptedData, string dataType) returns (bytes32)`

**作用**：写入一条新的健康数据链上记录。

**执行逻辑**：

- 基于 `msg.sender + dataHash + block.timestamp` 计算 `dataId`
- 校验 `dataId` 不重复
- 写入 `HealthRecord`（默认 `status=Private`，`isActive=true`）
- 将 `dataId` 追加到 `userRecords[msg.sender]`
- 触发 `DataStored` 事件
- 返回 `dataId`

### 5.2 `getHealthData(bytes32 dataId)`

**作用**：读取链上记录核心字段（需通过读权限校验）。

**返回字段**：

- `dataHash`
- `encryptedData`
- `timestamp`
- `owner`
- `dataType`

### 5.3 `updateHealthData(bytes32 dataId, bytes32 newDataHash, bytes32 newEncryptedData)`

**作用**：更新现有记录的哈希与加密摘要。

**权限**：owner 或具备写权限且未过期的授权地址。

**逻辑**：

- 校验记录仍为 `isActive`
- 更新 `dataHash`、`encryptedData`、`timestamp`
- 触发 `DataUpdated` 事件

### 5.4 `grantAccess(address requester, bytes32 dataId, bool canRead, bool canWrite, uint256 duration)`

**作用**：由 owner 向指定地址授予临时读写权限。

**关键限制**：

- 仅 owner 可调用
- `requester` 不能为空地址
- `duration > 0`
- 数据必须激活
- 仅 `Private` 数据可授权（公开数据不需要授权）

**结果**：写入 `permissions` 并触发 `AccessGranted`。

### 5.5 `revokeAccess(address requester, bytes32 dataId)`

**作用**：owner 撤销授权。

**逻辑**：

- 仅 owner 可调用
- 通过 `delete permissions[requester][dataId]` 清除授权
- 触发 `AccessRevoked`

### 5.6 `makeDataPublic(bytes32 dataId)`

**作用**：将数据由私密改为公开。

**逻辑**：

- 仅 owner 可调用
- 数据必须激活且当前为 `Private`
- 更新状态为 `Public`
- 触发 `DataStatusChanged`

### 5.7 `makeDataPrivate(bytes32 dataId)`

**作用**：将数据由公开改回私密。

**逻辑**：

- 仅 owner 可调用
- 数据必须激活且当前为 `Public`
- 更新状态为 `Private`
- 触发 `DataStatusChanged`

### 5.8 `getUserDataIds(address user)`

**作用**：返回某地址名下全部 `dataId` 列表。

### 5.9 `getUserDataCount(address user)`

**作用**：返回某地址名下记录数量。

### 5.10 `checkPermission(address requester, bytes32 dataId)`

**作用**：查询某地址在某条数据上的授权状态。

**返回**：

- `hasPermission`
- `canRead`
- `canWrite`
- `expiresAt`

当已过期时统一返回无权限。

### 5.11 `checkAccess(address requester, bytes32 dataId)`

**作用**：快速判断某地址是否具备读取能力。

**判定顺序**：

- 记录必须激活
- owner 直接可读
- 公开数据可读
- 私密数据需存在有效读权限

### 5.12 `getDataStatus(bytes32 dataId)`

**作用**：查询数据状态（`Private` / `Public`）。

### 5.13 `deleteData(bytes32 dataId)`

**作用**：删除数据（软删除）。

**逻辑**：

- 仅 owner 可调用
- 将 `isActive=false`
- 从 `userRecords[msg.sender]` 中移除该 `dataId`

注意：不是物理删除映射项，而是失活并移除用户索引。

### 5.14 `batchGrantAccess(address requester, bytes32[] dataIds, bool canRead, bool canWrite, uint256 duration)`

**作用**：对多条数据批量授权。

**逻辑**：遍历 `dataIds`，仅对 owner 本人持有的数据调用 `grantAccess`。

### 5.15 `getContractInfo()`

**作用**：返回合约统计信息。

**当前实现**：返回 `(0, 0)` 占位值，未维护真实计数器。

## 6. Solidity 自动生成的 Getter 说明

由于以下映射声明为 `public`：

- `healthRecords`
- `permissions`
- `userRecords`

Solidity 会自动生成同名 getter 方法。后端当前就直接使用了 `healthRecords(dataId)` 进行链上查询（见 `HealthDataChainService.get_health_record`），而不是调用 `getHealthData`。

这也是为什么后端读取到的字段包含：

- `data_hash`
- `encrypted_digest`
- `timestamp`
- `owner`
- `is_active`
- `data_type`
- `status`

## 7. 与后端调用关系（当前系统实际用到哪些方法）

结合 `backend/app/features/blockchain/service.py`，当前后端实际接入关系如下：

- `store_health_data(...)` -> 合约 `storeHealthData(...)`
  - 新增健康记录时调用
- `update_health_data(...)` -> 合约 `updateHealthData(...)`
  - 更新健康记录时调用
- `get_health_record(data_id_hex)` -> 合约自动 getter `healthRecords(dataId)`
  - 查询链上哈希用于校验

同时，后端会从 `DataStored` 事件中解析返回的 `dataId`，并写入数据库字段：

- `onchain_data_id`
- `onchain_tx_hash`

前端展示的“链上校验状态”来自后端比对“链上哈希 vs 当前数据重算哈希”的结果。

---

## 8. 当前合约实现的特点与边界

### 8.1 特点

- 提供了完整的 owner + 临时授权 + 过期控制模型
- 支持私密/公开状态切换
- 支持事件驱动的审计追踪
- 支持软删除与用户索引维护
- 适配“链下存主体数据，链上存校验凭证”的轻量上链模式

### 8.2 边界与限制

- `encryptedData` 仅为 `bytes32`，适合摘要，不适合大文本密文
- `getContractInfo` 目前为占位实现
- 后端当前未接入 `grantAccess/revokeAccess/makeDataPublic/makeDataPrivate` 等权限方法
- 项目中虽有其他合约文件（如 `Identity.sol`、`UserAuth.sol`），但当前业务主链路接入的是 `HealthDataAccess.sol`

---

## 9. 本节小结

本系统智能合约以 `HealthDataAccess` 为核心，实现了健康数据链上元数据存证、权限控制与状态管理。其方法体系围绕“写入、更新、读取、授权、撤销、状态切换、删除与查询”展开，能够为后端提供可验证的数据完整性依据。

从系统集成角度看，后端已接入该合约的核心写入与校验方法，完成健康数据“链下加密存储 + 链上哈希校验”的闭环；其余授权类方法为后续扩展（如第三方医疗机构按时授权访问）预留了实现基础。

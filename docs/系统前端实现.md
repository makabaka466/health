# 系统实现章节：前端实现

## 1. 前端总体实现思路

本系统前端采用 `Vue 3` 作为核心框架，结合 `Vue Router` 完成页面路由管理，使用 `Element Plus` 构建界面组件，并通过 `Axios` 封装统一的 HTTP 请求模块，实现与后端 `FastAPI` 接口的交互。整体上，前端采用“页面组件 + 路由守卫 + API 模块”的实现方式，使界面展示、状态控制和数据请求之间职责清晰，便于扩展与维护。

从代码结构来看，前端主要包含以下几个层次：

- **页面视图层**
  - 位于 `frontend/src/views`，负责页面展示、用户交互和局部状态管理。
- **路由控制层**
  - 位于 `frontend/src/router/index.js`，负责页面跳转、权限校验和用户端/管理端入口分流。
- **接口访问层**
  - 位于 `frontend/src/api/modules`，将认证、健康数据、智能问答、知识中心等接口进行模块化封装。
- **统一请求层**
  - 位于 `frontend/src/api/core/http.js`，负责统一注入令牌、处理超时与鉴权失败逻辑。

在路由实现上，系统将普通用户端和管理员端分为两套主入口：用户端使用 `/dashboard`，管理员端使用 `/admin`。其中用户端的首页、健康数据、智能问答、健康知识中心和个人中心作为子路由挂载在统一的 `Dashboard.vue` 布局中。该布局文件实现了左侧导航菜单、顶部面包屑、用户信息区域以及 `router-view` 内容插槽，从而形成一致的用户交互框架。

同时，前端在鉴权方面采用了本地存储配合路由守卫的方式：用户登录成功后，将令牌和角色信息保存到 `localStorage`；在页面跳转前，通过路由守卫判断当前目标页面是否需要认证、是否要求管理员权限，并自动完成未登录跳转和权限纠正。该实现保证了系统访问控制的基本安全性，也提升了多角色系统的使用体验。

## 2. 注册与登录页面的前端实现

### 2.1 注册页面实现

注册页面对应文件为 `frontend/src/views/Register.vue`。该页面主要基于 `Element Plus` 的 `el-form` 表单组件实现，包含用户名、邮箱、身份角色、管理员注册密钥、密码、确认密码等输入项。

在具体实现上，注册页面具有以下特点：

- **表单响应式建模**
  - 使用 `reactive` 定义 `registerForm`，统一管理注册输入数据。
- **前端表单校验**
  - 通过 `registerRules` 对用户名长度、邮箱格式、密码复杂度、确认密码一致性和是否同意协议进行校验。
- **身份差异化处理**
  - 当用户选择管理员身份时，页面会动态显示 `admin_register_key` 输入框；若重新切换为普通用户，则通过 `watch` 自动清空该字段。
- **密码强度提示**
  - 页面通过 `computed` 计算密码强度，并以进度条和文字形式提示“弱、中等、良好、强”，增强了交互性和安全提示能力。
- **协议与隐私政策弹窗**
  - 通过 `el-dialog` 展示用户服务协议与隐私政策内容，满足注册流程中的规范性要求。

当用户点击注册按钮后，页面执行 `handleRegister()` 方法。该方法先调用 `registerFormRef.validate()` 进行前端校验，校验通过后再调用 `registerUser()` 接口函数，将用户名、邮箱、密码、角色和管理员注册密钥传递到后端 `/auth/register` 接口。

注册成功后，前端不会直接登录，而是先弹出注册成功提示框。根据代码实现，提示框中会重点展示以下信息：

- 钱包地址
- 用户私钥
- 测试链发放的测试 ETH 信息（如果后端返回）

其中，私钥只在注册成功时展示一次，因此前端使用 `ElMessageBox.alert` 将其以强调形式展示，并提示用户必须手动保存。这一设计既反映了系统与区块链钱包绑定的业务特征，也体现了私钥不可重复获取的安全要求。随后，页面通过路由跳转到登录页，并携带 `username` 和 `registered=true` 查询参数，方便登录页自动展示“注册成功，请登录”的提示信息。

### 2.2 登录页面实现

登录页面对应文件为 `frontend/src/views/Login.vue`。该页面同样基于 `Element Plus` 表单组件构建，包含用户名、密码、记住我、忘记密码、第三方登录等功能入口。

从实现机制看，登录页面主要包括以下部分：

- **普通登录表单**
  - 使用 `reactive` 定义 `loginForm`，并通过 `loginRules` 实现用户名、密码长度校验。
- **注册成功回显**
  - 登录页通过 `useRoute()` 读取查询参数，当检测到 `registered=true` 时，利用 `el-alert` 显示注册成功提示，并自动填充用户名。
- **忘记密码弹窗**
  - 使用 `el-dialog` 与单独表单实现邮箱输入，但当前主要作为交互演示，内部通过延时模拟邮件发送。
- **第三方登录入口**
  - 页面提供微信与支付宝两个按钮，点击后分别调用 `handleSocialLogin('wechat')` 或 `handleSocialLogin('alipay')`。
- **首次社交登录资料补全**
  - 若后端返回 `need_profile_completion=true`，则自动弹出“首次第三方登录”对话框，引导用户补全用户名、邮箱和密码。

普通登录时，前端在 `handleLogin()` 中调用 `loginUser()`，该接口内部使用 `URLSearchParams` 将用户名和密码封装为表单格式，并提交到 `/auth/login`。登录成功后，前端执行 `persistLogin()`，将令牌和用户名写入本地存储，并根据角色自动分流：

- 普通用户跳转到 `/dashboard`
- 管理员跳转到 `/admin`

第三方登录流程则更具业务特点。前端先生成模拟授权码，并调用 `/auth/social/login-init` 接口。若后端判断为首次登录，则返回社交票据和建议用户名，前端随后弹出补全资料表单，调用 `/auth/social/complete` 完成账号绑定并登录。这样一来，前端不仅实现了传统账号密码登录，还实现了社交登录与补全流程的一体化交互。

### 2.3 登录注册的公共实现机制

在认证相关 API 调用方面，前端将逻辑统一封装在 `frontend/src/api/modules/auth.js` 中。主要接口包括：

- `registerUser()`：用户注册
- `loginUser()`：普通用户登录
- `adminLoginUser()`：管理员登录
- `socialLoginInit()`：第三方登录初始化
- `socialCompleteProfile()`：社交登录资料补全
- `upsertMyProfileData()`：更新用户资料

这些 API 最终都依赖 `createHttpClient()` 创建的请求客户端。统一请求模块会自动完成以下工作：

- 从 `localStorage` 读取普通用户或管理员令牌
- 自动在请求头中追加 `Authorization: Bearer <token>`
- 当后端返回 `401` 时自动清理本地认证信息，并跳转回登录页

因此，从实现角度看，注册登录功能不仅是界面层面的输入和按钮交互，更是路由控制、本地令牌管理和统一请求机制协同工作的结果。

## 3. 用户端主页的前端实现

用户端主页对应文件为 `frontend/src/views/Home.vue`，整体运行于 `Dashboard.vue` 统一布局内部。主页主要承担系统总览、快捷导航、推荐内容展示和 AI 个性化建议展示等功能。

### 3.1 页面布局实现

主页将内容划分为多个区域：

- 顶部欢迎信息与日期展示
- 快捷功能入口区域
- 系统概览卡片区域
- 最近活动区域
- 推荐文章区域
- 首页 AI 建议区域

其中，快捷功能入口 `quickActions` 通过数组配置方式实现，每个对象都包含标题、描述、图标、颜色和跳转路由。例如：

- 健康趋势 -> `/dashboard/health-data`
- AI 助手 -> `/dashboard/ai-chat`
- 个人中心 -> `/dashboard/profile`

这种方式的优点在于：前端无需为每个卡片单独编写跳转逻辑，只需通过统一的 `handleActionClick()` 调用 `router.push()` 即可完成页面导航，增强了组件化和可维护性。

### 3.2 推荐内容与首页智能建议实现

主页的动态数据主要来自两个接口模块：

- `knowledgeApi.getHomepageRecommendations()`
- `aiApi.getHomeAdvice()`

在推荐文章部分，前端调用知识中心接口获取“热门文章”和“最新文章”，再将两组数据合并去重，最终只保留前 5 条展示在首页。这一实现既利用了后端推荐结果，又通过前端去重逻辑避免重复内容，增强了页面展示质量。

在首页 AI 建议部分，前端通过 `loadAiHomeAdvice()` 调用 `/ai/home-advice` 接口，并将返回结果整理到 `aiHomeAdvice` 响应式对象中，包含：

- `summary`：建议摘要
- `recommendations`：健康建议列表
- `insights`：洞察内容
- `based_on_public_records`：建议依据的公开健康记录数量
- `updated_at`：更新时间

如果接口调用失败，前端不会直接报错中断页面，而是填充“个性化建议加载失败，请稍后重试”的兜底文本，从而保证页面结构完整。这种容错式设计符合论文中“前端异常处理”的描述要求。

### 3.3 页面刷新与状态同步实现

主页使用了 `onMounted`、`onActivated` 和 `watch(route.path)` 三种方式保证数据更新：

- 首次进入页面时调用一次数据加载函数
- 当页面从缓存中重新激活时刷新 AI 建议
- 当路由重新切换回 `/dashboard` 时再次刷新数据

这一机制与路由缓存配合使用，可以在保证性能的同时提升信息时效性。尤其是在用户刚刚修改公开资料或新增健康数据后，重新返回首页即可看到新的 AI 建议结果。

## 4. 健康数据页面的前端实现

健康数据页面对应文件为 `frontend/src/views/HealthData.vue`，是用户端最核心的业务页面之一。该页面不仅承担健康数据的增删改查，还实现了文件上传、数据格式转换、私密数据解锁和链上校验结果展示等功能。

### 4.1 页面数据组织与状态建模

页面中定义了多个响应式变量，用于分别管理：

- `healthRecords`：健康记录列表
- `healthSummary`：统计摘要信息
- `healthAnalysis`：健康分析结果
- `dialogVisible`：新增/编辑弹窗状态
- `isEditing`：当前是否为编辑模式
- `formMode`：当前录入模式（手动或文件）
- `privatePreviewDialogVisible`：私密数据预览弹窗状态
- `privatePreviewRecord`：当前预览的私密记录

此外，页面还使用了大量计算属性和辅助函数，例如：

- `statsCards`：顶部统计卡片
- `pdfRecords`、`wordRecords`、`manualRecords`：不同类型记录数量
- `privateRecords`、`publicRecords`：私密/公开记录数量
- `resolveOnchainLabel()`：链上校验状态显示文本
- `resolveOnchainTagType()`：链上状态标签颜色映射

由此可见，该页面并不是简单地展示接口数据，而是在前端进行了较为充分的结构转换和视图映射。

### 4.2 健康数据录入实现

健康数据页面支持两种录入方式：

- **手动录入模式**
- **文件上传模式**

当用户点击“新增手动记录”时，页面执行 `openManualDialog()`，将 `formMode` 设置为 `manual`，并重置健康表单；当用户选择文件上传时，则执行 `openFileDialog()`，将模式切换为 `file`。

在表单内容上，页面支持以下健康指标的录入：

- 身高
- 体重
- 血压
- 血脂
- 心率
- 血糖
- 其他说明

其中，血压字段并非简单文本存储，而是通过 `parseBloodPressure()` 将“舒张压/收缩压”格式拆分成结构化字段，随后在提交时与其他指标一起组织成 JSON 格式的 `data_content`。

提交逻辑由 `saveHealthData()` 完成，其主要流程如下：

1. 调用 `healthFormRef.validate()` 完成前端校验。
2. 根据录入模式构造后端需要的请求载荷：
   - 手动模式：构造 `data_content` JSON 字符串，并设置 `file_type='text'`
   - 文件模式：将上传文件通过 `FileReader.readAsDataURL()` 转换为 Base64，并传给 `pdf_data_base64`
3. 根据 `isEditing` 判断执行新增还是更新：
   - 新增调用 `healthApi.createRecord()`
   - 编辑调用 `healthApi.updateRecord()`
4. 操作成功后关闭弹窗，并重新调用 `loadHealthData()` 刷新页面数据。

### 4.3 文件上传与格式处理实现

健康数据上传部分支持 PDF 与 Word 文件。页面通过 `handleFileChange()` 对上传文件进行前端预处理：

- 根据文件 MIME 类型与文件后缀推断文件类型为 `pdf` 或 `word`
- 校验文件是否合法
- 控制文件大小上限
  - Word 不超过 `10MB`
  - PDF 不超过 `6MB`
- 使用 `FileReader` 读取文件为 Base64 Data URL，便于直接发送给后端接口

这种实现方式能够减少前端上传异常，同时与后端加密存储接口保持兼容。

### 4.4 私密健康数据展示实现

由于系统支持私密健康数据加密存储，因此健康数据页面在展示层增加了“私密数据自动解锁”逻辑。前端通过 `toViewRecord()` 将后端返回的健康数据对象转换为适合视图展示的结构，并额外保留：

- `requires_private_key`
- `is_private`
- `raw_content`
- 链上校验相关字段

当记录是私密数据时，页面不会直接展示内容，而是显示“未解锁”或隐藏状态。如果用户点击查看，则前端调用 `fetchUnlockedRecord()` 请求 `/health/records/{id}` 接口，尝试读取已解密后的内容。

若解密成功：

- 文本记录通过弹窗展示详细内容
- 附件记录直接通过 `window.open()` 或创建下载链接打开文件

若解密失败，则通过 `ElMessage.error` 反馈“当前账号缺少可用私钥”或“查看私密数据失败”。这一实现体现了前端对隐私控制和敏感数据访问约束的配合。

### 4.5 健康分析与统计实现

页面在加载时，会并行调用以下两个接口：

- `healthApi.getRecords()`：获取健康记录列表
- `healthApi.getSummary()`：获取摘要统计信息

前端通过 `Promise.all` 并行获取，提高了页面首屏效率。随后，页面根据返回数据构建统计卡片，例如：

- 记录总数
- 本月记录数
- 平均心率
- 最近记录时间

此外，用户还可以点击健康分析按钮，调用 `healthApi.analyzeData()` 获取健康分析结果。前端将返回内容写入 `healthAnalysis`，并通过提示消息反馈分析是否成功。这样，健康数据页面不仅是数据管理入口，也承担了数据解释与辅助分析的角色。

## 5. 智能问答页面的前端实现

智能问答页面对应文件为 `frontend/src/views/AiAssistant.vue`，其核心特点是实现了“历史会话管理 + 流式输出 + 私密数据上下文选择”的综合交互模式。

### 5.1 页面整体结构实现

页面主要划分为三大区域：

- **顶部标题区**
  - 展示“智能健康助手”标题和“新对话”按钮。
- **左侧历史对话区**
  - 显示历史聊天列表，支持点击切换不同会话。
- **右侧聊天主区域**
  - 展示消息记录、欢迎提示、快捷问题按钮、输入框和流式输出状态。

在无消息状态下，页面会显示欢迎界面与三个快捷按钮，例如“分析我的健康状况”“健康生活建议”“解释一下血压指标”。这类按钮通过 `sendQuickMessage()` 自动填充输入框并直接发送消息，降低了用户的使用门槛。

### 5.2 历史会话管理实现

智能问答页面通过以下接口管理会话数据：

- `aiApi.getChatHistory()`：获取历史会话列表
- `aiApi.getChatMessages(chatId)`：加载某个会话的详细消息

页面在 `onMounted()` 时会调用 `loadChatHistory()`，获取历史会话并显示在左侧栏；用户点击某个会话后，通过 `loadChat(chat.id)` 加载该会话中的消息内容，并滚动到底部。这一实现使系统具备持续对话能力，而不是一次性的问答交互。

### 5.3 流式问答实现

本页面最关键的实现点在于流式聊天。前端在 `frontend/src/api/modules/ai.js` 中并没有完全依赖 Axios，而是对 `/ai/chat/stream` 使用原生 `fetch` 实现 `SSE` 风格的流式读取。

具体而言，`streamMessage()` 的实现流程如下：

1. 通过 `fetch` 发起 POST 请求，并手动在请求头中附加 Bearer Token。
2. 使用 `response.body.getReader()` 逐块读取响应流。
3. 使用 `TextDecoder` 将字节流解码成文本。
4. 按 `\n\n` 分割事件块，并调用 `parseSseEvent()` 解析事件类型和数据。
5. 根据事件类型执行不同回调：
   - `meta`：记录会话 ID、参考来源、是否使用个性化数据
   - `status`：更新“正在检索知识库”“正在生成回答”等状态文本
   - `delta`：将增量回答内容逐步拼接到当前 AI 消息上
   - `done`：完成本次回答，并刷新聊天历史
   - `error`：提示错误信息

在页面层，`sendMessage()` 会先将用户消息插入本地消息数组，再创建一个空的 AI 消息对象用于承接流式内容。随后通过 `aiApi.streamMessage()` 将用户输入、当前会话 ID 和所选私密上下文记录一起发送给后端。随着后端持续返回 `delta` 事件，前端不断追加文本，并通过 `scrollToBottom()` 保持视图滚动到最新消息位置。

这种实现方式比传统“请求一次、等待整段文本返回”的方案更符合智能问答的实时交互特征，能够显著提升用户感知体验。

### 5.4 私密数据上下文选择实现

为了使 AI 回答更加个性化，页面设计了“选择私密数据”功能。实现方式如下：

- 点击“选择私密数据”按钮后，前端打开弹窗并调用 `aiApi.getPrivateContextOptions()`。
- 后端返回当前用户可授权用于问答的私密数据列表。
- 前端将这些数据渲染为复选框列表，用户可选择若干条记录。
- 选择结果保存在 `selectedPrivateContextIds` 中。
- 当用户发送消息时，前端会将这些 ID 一并写入请求体中的 `selected_private_context_ids` 字段。

在界面上，已选择的数据会以标签形式显示在输入区上方，用户可以随时删除选中的私密上下文项。此设计使用户对“哪些私密数据被用于问答”具有明确的可控性，也增强了系统的可解释性和隐私透明度。

### 5.5 错误处理与交互细节实现

页面还实现了以下增强机制：

- `AbortController` 支持中断流式输出
- `isTyping` 控制发送按钮和停止按钮显示逻辑
- `streamStatusText` 显示当前问答阶段状态
- 若发生超时或流式中断，前端给出更具体的提示语
- 消息附加区域会展示：
  - 是否使用了个性化数据
  - 是否使用了私密数据
  - 参考知识来源标签

因此，智能问答页面不仅完成了基础聊天功能，更实现了适用于健康场景的“可追踪、可中断、可解释”的智能交互流程。

## 6. 健康知识中心页面的前端实现

健康知识中心页面对应文件为 `frontend/src/views/KnowledgeCenter.vue`，主要实现文章浏览、分类筛选、关键词搜索、收藏管理和阅读历史查看等功能。

### 6.1 页面布局与内容展示实现

页面整体由“顶部工具栏 + 左侧分类栏 + 主内容区 + 阅读记录抽屉”构成。

顶部工具栏提供以下操作：

- 输入关键词搜索文章
- 查看全部文章
- 切换到“我的收藏”模式
- 打开阅读记录抽屉

左侧分类栏以按钮列表的形式呈现多个知识分类，如慢性病管理、营养饮食、心理健康等。每个分类对象都包含：

- 分类 ID
- 分类名称
- 图标
- 颜色
- 当前文章数量

主内容区支持两种展示模式：

- **卡片视图**
- **列表视图**

用户可以通过 `el-radio-group` 动态切换视图方式。卡片和列表两种模式共用同一套数据源，只是在渲染结构上有所区别。这种设计提高了界面灵活性，同时减少了重复的数据获取逻辑。

### 6.2 文章列表加载与分类搜索实现

知识中心页面的数据获取由 `loadKnowledgeItems()` 完成。该函数根据当前状态构造参数：

- `page`
- `page_size`
- `category`
- `keyword`
- `sort_by`

然后根据内容模式决定调用哪个接口：

- 普通模式下调用 `knowledgeApi.getArticles()`
- 收藏模式下调用 `knowledgeApi.getFavorites()`

后端返回分页结果后，前端会：

1. 将文章列表通过 `normalizeItems()` 统一补充 `is_favorited` 字段；
2. 更新总条数 `totalItems`；
3. 调用 `refreshCategoryCount()` 计算当前分类统计；
4. 根据分页状态更新页面内容。

当用户切换分类或执行关键词搜索时，页面会重置页码为第一页并重新加载数据。这样实现后，分类筛选与搜索逻辑可以自然叠加，满足知识检索类页面的使用需求。

### 6.3 收藏功能实现

收藏功能是知识中心页面的重要交互之一。前端通过 `toggleFavorite(item)` 完成收藏与取消收藏操作，具体过程如下：

- 若文章当前未收藏，则调用 `knowledgeApi.favoriteArticle(item.id)`
- 若文章当前已收藏，则调用 `knowledgeApi.unfavoriteArticle(item.id)`
- 根据接口返回结果更新：
  - `item.is_favorited`
  - `item.favorite_count`

为了防止重复点击，前端额外维护了 `favoritePendingIds` 数组。若某篇文章正在执行收藏请求，则按钮进入禁用状态，从而避免并发重复提交。

如果当前页面处于“我的收藏”模式，而用户执行了取消收藏操作，前端会直接将该文章从当前列表中移除，并同步更新总数。这种局部更新方式避免了整页重新加载，提高了交互流畅度。

### 6.4 阅读记录实现

知识中心页面通过 `openReadHistory()` 打开阅读记录抽屉，并调用 `knowledgeApi.getReadHistory(50)` 获取最近阅读记录。阅读记录包括：

- 文章标题
- 分类
- 最近阅读时间
- 阅读次数

页面中还定义了 `totalReadCount` 计算属性，用于统计抽屉内记录的累计阅读次数。用户点击某条阅读记录时，会关闭抽屉并跳转到对应文章详情页。该设计使知识中心不仅是阅读入口，也形成了用户阅读行为的可追溯展示。

### 6.5 与用户主布局的协同实现

除了知识中心页面本身，用户主布局 `Dashboard.vue` 还专门实现了“最近阅读”抽屉。顶部通知按钮点击后，会调用 `knowledgeApi.getReadHistory(12)` 拉取最近阅读内容并展示在全局布局中。

这意味着知识中心相关功能并不局限于单一页面，而是通过顶部导航与阅读历史机制扩展到整个用户端界面。其本质上体现了系统前端的模块协同设计：知识内容既可以在专属页面集中管理，也可以在主页和全局导航中被复用。

## 7. 前端实现特点总结

综合上述页面实现可以看出，本系统前端具有以下几个显著特点：

### 7.1 基于组件化页面的实现方式

系统将登录、注册、首页、健康数据、智能问答、知识中心等核心功能拆分为独立页面组件，并通过统一布局容器进行组织。这种实现方式增强了代码复用性，也便于后续继续扩展更多业务模块。

### 7.2 基于路由守卫的权限控制

系统通过 `Vue Router` 路由守卫，结合本地令牌与角色信息，实现了普通用户端与管理员端的自动分流及访问控制，保证了多角色系统的基本安全性。

### 7.3 基于模块化 API 的数据交互

系统将不同业务的接口分别封装在 `auth.js`、`health.js`、`ai.js`、`knowledge.js` 中，并统一使用 `http.js` 完成令牌注入和异常处理，使前端数据交互具有较好的结构性。

### 7.4 重视用户体验的交互设计

前端在多个页面中都实现了较细致的交互增强机制，例如：

- 登录注册中的动态提示、密码强度校验和弹窗补充流程
- 首页中的推荐内容和 AI 建议自动刷新
- 健康数据页面中的私密数据自动解锁和链上状态提示
- 智能问答页面中的流式输出和私密上下文选择
- 知识中心中的收藏、分类筛选、阅读记录与双视图切换

这些设计使系统不仅具备功能完整性，也具备较好的可用性和交互友好性。

### 7.5 面向健康场景的前端实现特色

与普通信息管理系统相比，本系统前端在健康场景下增加了明显的业务特色：

- 健康数据支持结构化录入与文件上传并存
- 私密健康数据在前端具有可见性控制
- AI 问答支持结合公开数据、私密数据和知识库进行回答
- 注册流程中融合钱包地址与私钥展示逻辑
- 健康记录支持链上校验状态展示

因此，本系统前端不仅完成了常规界面开发工作，还围绕“健康数据安全、知识服务与智能分析”这一主题进行了针对性的实现设计。
